# 시운전 데이터가 더 쌓였을 때 — PPT 갱신 절차

## 0. 이 환경에서 되는 것 / 안 되는 것

이 세션은 **클라우드 컨테이너**다. 저장소를 새로 복제해 둔 리눅스 상자이고,
발전소 사내망에는 붙지 못한다.

| | 여기서 되는가 | 근거 |
|---|---|---|
| Tool 시운전 — **데이터 취득** | **안 됨** | 취득은 RiMS/DataPARC **OPC UA 직결**(`cli.py`)이다. 사내망에 붙어야 한다 |
| 취득된 데이터로 **재계산** | **됨** | `gp.py` · `select.py` · `method_compare.py` 가 **표준 라이브러리만** 쓴다. numpy·scipy·sklearn 불필요 |
| PPT 재생성·검증 | **됨** | `build.js` + `verify.py` |
| Tool UI(PySide6) 코드 수정 | **됨** | 코드가 저장소에 있다 |
| Tool UI **화면 확인** | 시험 필요 | PySide6 미설치. pip 설치 후 `QT_QPA_PLATFORM=offscreen` 렌더가 되는지 봐야 안다 |

이 세션에서 실제로 돌려 본 결과 (2026-08-31, `python3 tool/scripts/method_compare.py`):

```
방식                     MAE     최대오차   미달   과대입찰합   기회손실합
일괄 보정 (종전 방식)      3.833   10.395   14건     65.4      68.4
GP (현재 툴 기본)         1.294    4.165    3건      7.6      29.1
```

**장표에 실린 수치가 그대로 재현된다.** 즉 데이터 파일만 새것으로 바뀌면
이 세션에서 전 수치를 다시 계산해 PPT 에 반영할 수 있다.

## 1. 권장 절차

```
① 부장님 PC        평소대로 Tool 시운전 → 결과가 누적 데이터에 반영
② 부장님 PC        갱신된 데이터 파일을 커밋·푸시
                     tool/wirye_capacity/data/measurements_seed.json  (또는 store 파일)
③ 이 세션          git pull → 재계산 → PPT 재생성 → 기하 검증
```

②를 못 하는 상황이면 **파일을 대화창에 올려 주셔도** 되고, 회차 몇 건이면
`날짜 / CIT / 대기압 / 습도 / CC / 진공도 / IGV 여부` 를 적어 주셔도 된다.

## 2. 세션끼리 데이터를 주고받는 방법

**세션끼리 파일을 직접 주고받는 길은 없다.** 공유 매개는 **저장소(git)** 하나뿐이다.
"저 세션에서 돌려서 이 세션으로 보내라"는 성립하지 않는다 — 그 세션도 클라우드면
사내망에 못 붙어 시운전 자체를 못 하고, 결과를 넘길 방법도 커밋뿐이다.
(그 세션이 **부장님 PC 에서 도는 로컬 Claude Code** 라면 시운전은 가능하다.
그래도 이 세션으로 넘기는 길은 여전히 커밋·푸시다.)

### 두 세션을 동시에 쓸 때의 규칙

같은 브랜치를 두 세션이 만지면 충돌한다. 역할과 브랜치를 나눈다.

| 세션 | 맡는 것 | 브랜치 |
|---|---|---|
| 이 세션 | PPT 18장 · Tool UI 디자인 | `claude/yirye-capacity-ppt-91eg5n` (+ UI 는 별도 브랜치) |
| 기존 세션 | 도구 로직 · 데이터 취득 | 자기 브랜치 |

## 3. 지금의 약점과 개선안 — 수치가 10개 파일에 흩어져 있다

현재 장표 수치는 슬라이드 파일에 직접 적혀 있다.

| 수치 | 들어 있는 파일 |
|---|---|
| 3.83 → 1.29 · 14 → 3 · 65.4 → 7.6 | `s01` `s03` `s14` `s18` |
| 실측 36건 산점도 · 오차 상위 4회차 | `s06` |
| BLT 적용값 16회차 | `s05` |
| 온도 구간별 건수 | `s10` `s12` |
| 커널 7종 MAE · 방식별 곡선 | `s11` |
| 시운전 4회차 실측 | `s14` |

데이터가 바뀌면 **10개 파일을 손으로 고쳐야 한다.** 회차가 계속 쌓일 것이므로
한 번은 정리해 두는 편이 낫다.

### 적용 완료 (2026-09-01) — `deck_data.json` + `refresh_data.py`

```
tool/wirye_capacity/data/  ──(읽기)──▶  docs/ppt/build/refresh_data.py
                                              │  전부 다시 계산
                                              ▼
                                    docs/ppt/build/deck_data.json
                                              │
                     slides/*.js 가 이 파일 하나만 참조
```

데이터 갱신이 **명령 세 줄**로 끝난다.

```bash
python3 docs/ppt/build/refresh_data.py    # 데이터 → 수치 재계산
node    docs/ppt/build/build.js           # 18장 재생성
python3 docs/ppt/build/verify.py          # 기하 검증
```

`refresh_data.py` 가 계산할 것 — 36건 산점, 일괄 baseline(평균)과 LOOCV MAE·RMSE,
구간별 건수, 오차 상위 4회차, 커널 7종 LOOCV, 방식별 보정 곡선, 미달·과대 누계.
전부 기존 도구 코드(`gp.py` `select.py` `margin.py`)를 그대로 호출한다 —
**장표용으로 따로 계산하지 않는다.** 그래야 화면 값과 장표 값이 어긋나지 않는다.

BLT 적용값 16회차와 시운전 함정 3건은 계산이 아니라 기록이므로 손으로 둔다.

#### 처음 돌렸을 때 드러난 것 (2026-09-01)

| | 장표에 적혀 있던 값 | 데이터에서 나온 값 |
|---|---|---|
| 시운전 회차 | 4회차 | **5회차** (2026-04-15 ~ 07-29) |
| 시운전 치우침 | +0.14 | **+0.24** MW |
| 시운전 평균 오차 | 1.36 | **1.21** MW |
| 시운전 큰 오차 | 1.57 | **1.43** MW |

나머지(커널 7종 MAE·일괄 3.833·미달 14→3·과대 65.4→7.6·오차 상위 4회차·
방식별 곡선)는 **소수점까지 그대로 일치**했다. 손으로 옮긴 값이 맞았다는 뜻이고,
동시에 회차가 쌓이면 이렇게 조용히 낡는다는 뜻이기도 하다.

## 3.5 정본 규약 — CIT 소수점 (2026-09-01 확정)

같은 회차에 두 값이 나온다. **담당자 표 쪽을 정본으로 한다.**

| 경로 | CIT | 이론 | 보정값 | 정본 |
|---|---|---|---|---|
| 담당자 Base Load 실적표 전사 (1 소수점) | 37.9 | 359.78 | **+1.42** | **○** |
| Tool 자동 취득 (산정 탭·DB, 2 소수점) | 37.92 | 359.72 | +1.48 | |

근거 — `measurements_seed.json` 의 기존 36건이 전부 1 소수점이고,
`tool/scripts/data/commission_2026.csv` 의 기존 5회차와 **불일치 0건**이었다.
이미 그 규약으로 쌓여 있으므로 바꾸면 과거와 어긋난다.

따라서 출력 시뮬레이션 탭이 보여주는 값이 정본과 같다. 앞서 "시뮬 탭 반올림 버그"
라고 적었던 것은 **버그가 아니라 두 경로의 규약 차이**였다 — 정정한다.

## 4. 회차 하나를 진행하는 법 — `trial.py`

예측을 **실측 전에** 남기고, 실측이 나오면 대조한다. 계산은 도구 코드가 한다
(`store.build_record` · `select.predict` · 신고값 식은 `method_compare` 와 동일).

```bash
# ① 실측 전 — 신고 직전. 예측이 원장(trial_log.json)에 남는다
python3 docs/ppt/build/trial.py predict --date 2026-08-12 --cit 30.2 --press 1004.3 --rh 62.5

# ② 실측이 나온 뒤 — 예측과 대조하고 누적에 반영 (--apply 없으면 미리보기)
python3 docs/ppt/build/trial.py record --date 2026-08-12 --cc 384.1 --apply

# ③ 원장 요약
python3 docs/ppt/build/trial.py status
```

② 는 ① 에서 준 값(CIT·대기압·습도·IGV)을 자동으로 이어 쓴다. 두 번 적지 않는다.

### 왜 예측을 먼저 남기는가

시운전에서 재는 것은 **'반영 전에 낸 예측이 실측과 얼마나 맞았는가'** 다
(`commission_stats.py` 의 정의). 실측을 보고 나서 채점해도 코드가 그 회차를
학습에서 빼주므로 방법론상 문제는 없다. 그러나 **예측을 먼저 적어 둔 기록**이
있으면 "맞히고 나서 설명한 것이 아니다" 를 증명할 수 있다. 발표에서 이 차이는 크다.

### 반영 가드 — 계획서 §6 '시운전 함정' 을 그대로 건다

| 상황 | 주는 인자 | 결과 |
|---|---|---|
| IGV Turn-up 미실시 | `--no-igv` | **누적 반영 차단.** 원장에는 남고 학습에서만 빠진다 (함정 1) |
| 습도계 두 대가 벌어짐 | `--rh2 19.6` | 차이가 `--rh-gap`(기본 10%p)을 넘으면 **반영 보류** (함정 2) |

가드에 걸리면 `--apply` 를 붙여도 누적에 들어가지 않는다. 값은 원장에 남으므로
나중에 원인이 밝혀지면 되살릴 수 있다.

> `--rh-gap` 기본 10%p 는 **이 스크립트의 선별 기준**이지 도구의 상수가 아니다.
> 실제로 겪은 사례는 취득 19.6% vs 실제 68.5% — 48.9%p 벌어진 건이었다.
> 현장 기준이 따로 있으면 그 값으로 바꾼다.

#### 캡쳐로 데이터를 주실 때

Tool 의 시뮬레이션·산정 결과 화면을 캡쳐해 올려 주시면 읽어서 반영할 수 있다.
다만 **내가 화면에서 옮겨 적는 단계**가 생기므로, 읽은 값을 표로 되돌려 드려
맞는지 확인받은 뒤에 데이터에 넣는다. 캡쳐에 이 항목이 보이면 된다.

    날짜 · 외기온도 CIT · 대기압 · 상대습도 · CC Gross 실측 · 진공도 · IGV 실시 여부

`measurements_seed.json` 파일을 그대로 올려 주시는 편이 옮겨 적는 단계가 없어
가장 안전하다.
