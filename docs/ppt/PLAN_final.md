## 0. 발표 조건

| 항목 | 내용 |
|---|---|
| 대상 | 본사 직책자 (의사결정자, 기술 세부보다 판단 근거를 본다) |
| 시간 | **발표 10분 + Tool 시연 3~4분** |

| 목차 | **7개 (지정)** — 아래 원문 그대로 |
| 산출물 | `.pptx` — 발표자가 직접 수정 가능해야 함 |

### 목차 7개 — 지정 원문 (2026-08-31 수령)

```
1. 개요 및 추진 배경
2. 현황 파악 및 문제 정의
3. 데이터 분석 및 원인 규명(가설 검증)
4. 해결 방안 도출 및 예측/보정 모델 개발
5. 향후 추이 분석(모니터링 체계 구축)
6. 개선 효과(정량적/정성적)
7. 향후 계획 및 수평 전개 방안
```

이 7개가 **목차 장과 본문 15장 머리글의 원본**이다. `docs/ppt/build/theme.js` 의
`INDEX` 상수 한 곳에만 두었으므로, 표현을 고치면 목차 장과 머리글이 함께 바뀐다.
머리글은 `04   해결 방안 도출 및 예측/보정 모델 개발   ·   모델 선정` 처럼
목차 명칭 + 그 장의 세부 라벨로 나온다.

> 6번 원문은 `개선 효과(정량적/정석적)` 로 받았는데 **정성적**의 오타로 보아 그렇게 넣었다.
> 아니면 알려 주시면 상수 한 줄만 고친다.

**직책자 발표의 전제 3가지**
1. **결론이 앞에 있어야 한다.** 2번 슬라이드에서 이미 답이 보여야 한다.
2. **한 장에 메시지 하나.** 나열하면 흐름을 잃는다.
3. **숫자는 비교로 보여야 한다.** 절대값 하나는 의미가 없고 before/after가 의미다.

## 1. 핵심 메시지 — 이 발표가 남길 한 문장

> ### 사람의 판단 하나였던 보정값을, **데이터가 스스로 갱신하는 모델**로 바꿨습니다.

부제로 쓸 수치 세 개 (표지·요약·마무리에 반복 노출):

```
예측오차   3.83 → 1.29 MW   (66% ↓)
미달 회차  14건 → 3건        (79% ↓)
과대입찰   65.4 → 7.6 MW     (88% ↓)
```

*(누적 36건 LOOCV 기준. 종전 = 일괄 보정, 개선 = GP·RBF)*

## 2. 스토리라인 — 7개 목차를 하나의 흐름으로

```
매주 신고하는 숫자가 있다
      ↓  그 숫자를 온도와 무관한 '하나의 보정값'으로 맞춰 왔다
실제 편차는 -4.9 ~ +12.9 MW 로 온도에 따라 갈린다
      ↓  하나로 맞추면 겨울엔 과소(기회손실), 여름엔 과대(페널티)
왜 갈리는가 — 가설 4개를 세우고 3개를 데이터로 기각했다
      ↓  그럴듯한 설명을 계속 무너뜨린 끝에 남은 것: 온도 의존 잔차
물리 이론은 동결하고, 잔차만 온도별로 학습한다 (2단 구조)
      ↓  데이터가 36건뿐이라는 제약 — 커널 5종 · LOOCV · 층화 분리로 넘었다
커널 7종을 같은 자리에서 채점 → GP·RBF 가 전 지표 1위
      ↓  시운전에서 함정 3개를 만나고 전부 코드 가드로 못박았다
회차가 쌓이면 LOOCV 재학습으로 최적 모델을 다시 고른다 (자기 갱신)
      ↓
효과: 정량 3지표 + 정성 4관점 → 같은 구조 입찰 사업소로 수평 전개
```

**서사의 축은 "정확도 개선"이 아니라 "판단의 근거화"다.**
직책자가 사는 것은 MW 개선치가 아니라 *왜 그 숫자인지 설명할 수 있게 됐다*는 것이다.

## 3. 언어 원칙 — 전문용어를 쓰지 않는다

**대상은 본사 직책자다. 데이터 전문가가 아닌 분이 대부분이다.**
슬라이드에서 설명이 필요한 단어가 나오면 그 순간 청중은 내용을 놓친다.

### 규칙 3개

1. **슬라이드 본문은 쉬운 말로.** 전문용어는 괄호에 작게 병기한다.
   → `평균 오차 1.29 MW (MAE)` 처럼. 엔지니어도 헷갈리지 않고, 비전문가도 안 막힌다.
2. **제목은 라벨이 아니라 문장으로.**
   → ~~"가설 검증"~~ → **"그럴듯한 설명 4개를 의심했고, 3개는 틀렸습니다"**
3. **숫자에는 항상 방향을 붙인다.**
   → ~~"R² 0.85"~~ → **"설명력 0.85 — 1에 가까울수록 좋음"**

### 용어 치환표 (슬라이드에 쓸 표현)

| 원래 용어 | 슬라이드 표현 | 필요하면 이렇게 한 줄 설명 |
|---|---|---|
| LOOCV | **한 건씩 가리고 맞혀보기** | 정답 하나를 가리고 나머지로 맞혀본다. 36번 반복 — 모의고사와 같다 |
| MAE | **평균 오차** | 평균적으로 몇 MW 틀렸나 |
| RMSE | **큰 오차 가중 지표** | 크게 틀린 경우에 벌점을 더 준 오차 |
| R² | **설명력** | 0~1. 1에 가까울수록 잘 설명한다 |
| GP (가우시안 프로세스) | **부드럽게 잇는 방식** | 데이터가 있는 곳은 따르고, 없는 곳은 완만하게 잇는다 |
| 커널 (RBF·Matérn 등) | **잇는 방식** | 점과 점 사이를 어떤 모양으로 이을지 정하는 규칙 |
| 하이퍼파라미터 | (슬라이드에 쓰지 않음) | 사람이 정하지 않고 데이터가 정한다고만 말한다 |
| 잔차 | **이론과 실제의 차이** | |
| 층화 추출 | **온도대별로 골고루 나눠 뽑기** | 한쪽 온도대가 통째로 빠지지 않게 |
| 편차(bias·ME) | **치우침** | 계속 낮게 신고하는지 높게 신고하는지 |
| 허용밴드 | **허용 오차 범위 (±0.5%)** | |
| 스킬 점수 | **종전 방식 대비 개선율** | |
| 상관계수 r | **관련성** | +1 / −1 에 가까울수록 강한 관계 |
| 센서 드리프트 | **센서 값이 서서히 어긋나는 현상** | |
| OPC UA | **표준 통신 방식** | RiMS 서버와 직접 주고받는 산업 표준 |
| 2단 구조 | **이론 층 + 실적 보정 층** | |
| 내포 W | **숨어 있던 IGV 효과** | |
| 미달 / 과대입찰 / 기회손실 | (그대로 — 실무 용어) | |
| 보정값 | (그대로 — 담당자가 쓰는 말) | |

### 컴팩트판(v2) 용어 정책 — **용어는 그대로 쓰고, 첫 등장에 한 줄 설명** (2026-09-02 확정)

한 번 반대로 갔다가 되돌렸다. 컴팩트판을 만들 때 전문용어를 아예 쉬운 말로
바꿔치웠는데(예: `MAE` → `신고값이 실제와 어긋난 정도`) 두 가지가 나빠졌다.

1. **수치가 무슨 지표인지 사라졌다.** 발표 후 자료만 다시 볼 때 `1.29 MW` 가
   어떤 지표인지 되짚을 단서가 없다. 사내 문서·도구 화면은 `MAE` 로 쓴다.
2. **엔지니어 청중이 오히려 막혔다.** 아는 용어를 낯선 풀이말로 바꾸면
   "그게 MAE 말하는 건가?" 를 속으로 번역해야 한다.

그래서 규칙을 이렇게 고정한다.

| | 규칙 |
|---|---|
| 용어 | **원래 용어를 그대로 쓴다** — MAE · RMSE · R² · 커널 · LOOCV · 상관계수 r · 이론값 · 보정값 |
| 첫 등장 | 그 용어가 **처음 나오는 장에서 한 줄로 풀어 준다.** 이후 장에서는 반복하지 않는다 |
| 큰 수치 | 숫자 옆(또는 아래)에 **이게 무슨 숫자인지 한 마디.** 예 — `예측 오차 · MAE` / `신고할 값을 미리 계산했을 때 실제와 벌어진 폭의 평균. 작을수록 좋습니다.` |
| 방향 | 항상 붙인다 — "작을수록 좋음" / "1 에 가까울수록 좋음" |

**첫 등장 장** (여기서 한 줄 설명이 나온다)

| 용어 | 첫 등장 | 그 장에 적은 설명 |
|---|---|---|
| 이론값 | 4·5장 | 온도·대기압·습도·복수기 진공도로 계산한 값 (보정 없음) |
| 보정값 | 5장 | 실제 − 이론값 − W(IGV) |
| 상관계수 r · 임계값 | 6장 | 0 에 가까우면 관계 없음 / 임계 ±0.31 을 넘지 못하면 우연으로 본다 |
| IGV | 7장 | 공기 흡입량을 늘리는 조작 |
| MAE · RMSE · R² · 커널 · LOOCV | 9장 | MAE 평균 오차 · RMSE 크게 틀린 경우에 벌점을 더 준 오차 · R² 설명력 · 커널 점과 점 사이를 어떤 모양으로 이을지 정하는 규칙 · LOOCV 한 회를 가리고 나머지로 맞혀보기 |
| 외삽 금지 | 8장 | 실측 범위 밖은 끝값을 유지한다 |

> 18장판(`slides/`)은 종전 정책("쉬운 말 + 괄호에 용어")을 그대로 둔다.
> 두 판을 같은 정책으로 맞출 필요는 없다 — 18장판은 상세 설명용이다.

**시험 방법**: 각 슬라이드를 발전 업무를 모르는 사람에게 읽혔을 때
"무슨 말인지는 알겠다"가 나와야 한다. 안 나오면 그 문장은 고친다.
컴팩트판은 여기에 하나 더 —
**"이 숫자가 무슨 숫자인지 슬라이드 안에서 알 수 있다."**

## 4.1 컴팩트판(v2) — 전체 14장 / 본문 11장

18장판은 한 장에 요소가 3~4개라 "어디를 봐야 하는지" 가 흐렸다. 그래서 **디자인은
그대로 두고 밀도만 낮춘** 판을 따로 만든다. 두 판은 함께 유지한다 — 18장판은
상세 설명용, 컴팩트판은 실제 발표용이다.

**장수 이력** — 13장(본문 10) → 15 → 16 → **14장(본문 11)**.
2026-09-04 검토에서 두 장을 줄였다 — 가설 검증 장(통계 용어가 많아 직책자
자리에서 읽히지 않는다)을 없애고 결론만 6장 리드로 흡수, Tool 두 장(기능·시연)을
한 장으로 합쳤다. 14장 × 43초 ≈ 10분.

**컴팩트 규칙** (모든 장에 적용)

| 규칙 | 값 | 왜 |
|---|---|---|
| 한 장의 요소 수 | **2개** | 눈이 갈 곳을 둘로 줄인다 |
| 리드 문장 | **1~2줄** | 제목이 이미 결론이다 |

### 4.1.5 2026-09-05 전면 검토 반영 — 채점 집합 통일과 사실 정정

**① 채점 집합을 39회 하나로 통일했다.** 종전에는 같은 '예측 오차' 가 3장에서
1.29(40회 전체), 8장 표에서 1.301(7가지 공통 39회)로 두 값이 나왔다.
`refresh_data.common_set()` 이 7가지가 모두 예측 가능한 회차를 골라
`bid_impact`·`blanket_loocv`·`select.loocv` 가 **같은 자리**에서 채점한다.
빠지는 한 회차는 20~25℃ 구간의 유일한 회차다 — 그 회차를 빼면 구간이 비어
구간평균이 예측을 못 한다.

| | 종전(40회) | 현재(39회) |
|---|---|---|
| 예측 오차 | 3.80 → 1.29 (66%↓) | **3.90 → 1.30 (67%↓)** |
| 기준 미달 | 15 → 4회 (73%↓) | 15 → 4회 (73%↓) |
| 과대 신고 | 69.5 → 9.3 MW (87%↓) | 69.5 → 9.3 MW (87%↓) |
| 기회손실 누계 | 75.5 MW | 75.3 MW |

기준선 `+2.5`(그림의 수평선)만 **40회 전체 평균** 그대로다 — 채점 결과가
아니라 '종전에는 이 숫자 하나였다' 는 설명용 상수이기 때문이다.

**② 사실과 달랐던 문구를 고쳤다.** 10·11장의 "실측 전에 예측을 기록했습니다"
는 사실이 아니었다 — `trial_log.json` 의 `pred_corr` 가 전부 `null` 이다.
실제로 한 것은 walk-forward 재현(각 회차를 **그 앞의 데이터만으로** 예측)이고,
그렇게 고쳐 적었다. 실측 전 예측을 남기는 기능(`trial.py predict`)은 도구에
이미 있으므로 **앞으로의 계획**으로 10장 결론에 한 줄 남겼다.

**③ 5장 세로축에서 W(IGV)가 빠져 있었다.** 보정값 정의는
`실측 − 이론기준값 − W(IGV)`(`correction.py:14`)인데 라벨은 "실제 − 이론값"
이었다. 여름 극값 회차(2026-07-22)는 실제로는 이론값보다 **+1.15 MW 더**
나왔는데(W +6 을 올려서) 슬라이드는 "5 MW 덜" 로 읽혔다.

**④ '이론값' 이 장마다 다른 것을 가리켰다.** 5·7장은 이론기준값(W 제외),
9·14장 프로파일 곡선은 `cc_theory`(W 포함)다. 9·14장 라벨을
**"이론 출력 (IGV 포함 · 보정 없음)"** 으로 바꿔 구분했다.

그 밖에 목차 페이지 번호(7장 삭제 후 미갱신), '대습도' 오타
(`label.slice(-3)` 버그), 여름 기준 온도를 세 장에서 하나로, 어투 4건,
설명 보강 5건을 함께 고쳤다. 상세는 `docs/ppt/REVIEW_2026-09-05.md`.

### 4.1.3 Tool 화면 캡처 — 어디서 오나

발표자료에 목업을 넣지 않는다. 그림은 전부 실제 화면이고, 다음 한 줄로 다시 뽑는다.

```bash
python3 tool/scripts/ui_shot.py docs/ppt/assets --clean --size 1280x860 \
        --run-profile 2026-08-26 \
        --shots tool_window,tool_input,tool_profile,tool_curve,tool_models,tool_list,tool_status
```

| 옵션 | 왜 필요한가 |
|---|---|
| `--clean` | 첫 실행 안내 띠와 상태줄에 임시 DB 경로(`/tmp/...`)가 찍힌다. 발표자료에 그 경로가 보이면 안 된다 |
| `--shots` | 픽셀 좌표로 자르지 않고 위젯을 직접 잡는다. 화면 레이아웃이 바뀌어도 잘리는 자리가 틀어지지 않는다 |
| `--run-profile` | 산정 탭 표는 실행 전에는 비어 있다. 빈 표를 실을 수 없으니 한 번 돌려 채운다(취득만 시드 기반 Mock, 계산 경로는 같다) |

**그림 크기는 원본 비율 그대로 넣는다.** 늘리면 글자가 뭉개지고, 그러면 도구가
지저분해 보인다. 슬라이드 코드에 원본 픽셀을 적어 두고 비율을 계산한다.

> ⚠ **캡처는 `claude/tool-v2` 브랜치의 다크 테마 화면이다.** 그 브랜치가 병합되기
> 전에 발표하면 실물(현재 밝은 테마)과 색이 다르다. 발표 전에 병합 여부를 확인한다.

`verify.py` 도 함께 고쳤다 — 종전에는 그림을 여백·겹침 검사에서 뺐다. 캡처를
잘못 놓아 여백을 침범하거나 글자를 덮어도 '통과' 로 나왔다. 이제 그림도 본다.

> **일 처리 시간(분)은 적지 않았다.** 종전 절차에 실제로 몇 분 걸렸는지 측정 기록이 없다.
> 대신 **셀 수 있는 것만** 적었다 — 엑셀 파일 4개 → 도구 1개, 손으로 옮겨 적는 값 61개 → 0개,
> 입력 1곳(날짜·시각). 종전 소요 시간을 알려주시면 그 자리에 넣는다 (§9 Q9).

### 4.1.2 6장 원인 규명 — 왜 이 순서인가

| 단계 | 무엇을 재나 | 결과 |
|---|---|---|
| ① 원시 | 보정값 vs 후보 | 넷이 다 강하다 — 온도 −0.84 · 진공도 −0.82 · 대기압 +0.73 · 습도 −0.73 |
| ② 온도를 **직선**으로 뺀 뒤 | 온도로 설명 안 되는 후보 vs 온도로 설명 안 되는 보정값 | 진공도 −0.15 · 대기압 +0.12 (임계 0.31 미달 → 사라짐) · **습도 −0.41 은 남는다** |
| ③ 온도를 **곡선**(LOOCV 모델)으로 뺀 뒤 | 후보의 온도 잔차 vs 모델이 못 맞힌 부분 | 진공도 +0.00 · 대기압 −0.13 · 습도 −0.24 — **전부 임계 미달** |

②에서 습도가 남고 ③에서 사라진 것이 이 장의 핵심이다. **온도와 보정값의 관계가
직선이 아니라는 증거**이고, 곧 다음 장(커널로 곡선을 학습)의 근거가 된다.
후보들이 서로 온도에 묶여 있다는 것도 함께 적는다 — 온도와의 r 은
진공도 +0.95 · 대기압 −0.83 · 습도 +0.67.

| 지표 대비 | 취소선 + 두 줄 막대 | **계기 눈금 게이지** (종전 눈금 → 개선 침) | 같은 정보를 이 과제의 언어로 말한다 |
| 활자 계급 | 숫자 46px / 나머지 13.5px — **2단** | **4단** (데이터·주장·본문·라벨) | 2단뿐이라 숫자만 튀고 글이 한 덩어리로 읽혔다 |
| 글 / 데이터 | 같은 바탕에 나란히 | **데이터는 홈 면, 글은 바탕** | 종류가 크기보다 먼저 색면으로 갈린다 |
| 과거/현재 비교 | 112px 한 덩어리 · 칩 9.5px | **148px 두 덩어리 · 칩 13px** | 상단 룰을 슬레이트/앰버로 갈라 색으로도 구분 |

**유지한 것** — 그래프·차트·구성(회신에서 좋다고 한 부분), 색의 뜻 고정, 하단 결론 한 줄,
문장형 제목, 샘플 03 수준의 정보 밀도.

**표지 히어로 교체** — 큰 타이틀 + KPI 나열 대신, **일괄 보정 수평 점선(종전 +2.4)과
GP·RBF 실측 보정곡선(0℃ +7.50 → 30℃ −2.38)이 교차하는 그래프**를 우측에 앉혔다.
이 과제의 결론이 표지에서 그림 한 장으로 읽힌다 (겨울 5.1 MW 과소 / 여름 4.8 MW 과대).

### 5.1 (폐기 · 이력용) 참고 샘플에서 가져왔던 12가지

> ⚠️ **이 절은 v2 에서 폐기했다.** 여기 적힌 12개가 곧 모방의 원인이었다.

```
      #A8BCD1  밝은 슬레이트 (종전 방식 — 선: 그래프의 점선·침)

      #2C425A  헤어라인 / #1F3244 더 약한 헤어라인

```

**색의 의미를 고정한다 — 이게 이 발표의 핵심 장치다.**

| 색 | 뜻 | 쓰이는 곳 |
|---|---|---|
| 슬레이트 회색 | **종전 방식** | 일괄 보정 막대, 종전 눈금 |
| 놋쇠 앰버 | **개선 결과** | GP 막대·곡선, KPI 숫자, 결론 강조어 |
| 레드 | **위험·미달** | 미달 회차, 기각된 가설, 함정, 손실 구간 |

색만 보고도 "회색은 옛것, 앰버는 새것, 빨강은 위험"이 읽히게 한다.
슬라이드마다 색 뜻이 달라지면 청중은 매번 범례를 다시 읽어야 한다.

**선은 면보다 한 톤 밝게** — 2px 선은 같은 색의 채워진 면보다 훨씬 어둡게 보인다.
종전 방식을 막대·박스로 그릴 때는 `#5E7793`, **그래프의 점선·게이지 침으로 그릴 때는
`#8CA3BC`** 를 쓴다 (홈 면 위 대비 4.2:1 → 7.2:1). 굵기도 개선 곡선과 같은 2.6px 로 맞춘다 —
before/after 는 대등한 한 쌍이므로 한쪽만 얇으면 비교가 성립하지 않는다.

### 회색이 안 보이던 이유 — 명도가 아니라 색상 (2026-08-31 3차 회신)

회신: *"빨간색·노란색·흰색 글자는 잘 구분되는데 회색 글자가 은근히 잘 안 보인다."*

원인은 명도가 아니라 **색상**이었다. 남색 바탕(`#0F1A28`)에 **푸른 회색** 글자를 얹으면
명도차가 있어도 색상이 같은 계열이라 바탕에 묻힌다. 빨강·노랑·흰색이 잘 보였던 것은
색상이 반대편이라 명도 말고 색상으로도 갈렸기 때문이다.

→ **중립색 계열을 전부 '따뜻한 회색'으로 돌렸다.** 종전 방식(슬레이트)만 푸른 계열로
남긴다 — 앰버(개선)와 반대편이어야 뜻이 갈리기 때문이다.

| 용도 | 이전 | 현재 | 대비 (배경 기준) |
|---|---|---|---|
| 본문 문장 | `#BCC9D6` | **`#CFCBC2`** | 10.4 → **10.8 : 1** |
| 캡션·부가 | `#93A6BA` | **`#A9A79F`** | 7.0 → **7.3 : 1** |
| 라벨 | `#63798F` | **`#8A8880`** | 3.9 → **4.9 : 1** |
| 종전 — 면 | `#5E7793` | **`#718BA6`** | 3.8 → **5.0 : 1** |
| 종전 — 선 | `#8CA3BC` | **`#A8BCD1`** | 6.7 → **9.0 : 1** |

**진단의 근거** — 본문은 바꾸기 전에도 이미 **10.4:1** 이었다. 그런데도 안 보였다는 것이
명도 문제가 아니라는 증거다. 색상을 바꾼 것이 효과의 대부분이고, 명도는 부수적으로
올렸다. 다만 라벨(3.9:1)과 종전 면(3.8:1)은 WCAG AA(4.5:1) 미달이기도 했다.
이제 전 색이 AA 를 넘는다: 회백 14.2 · 본문 10.8 · 앰버 9.2 · 종전선 9.0 · 캡션 7.3 ·
레드 5.4 · 종전면 5.0 · 라벨 4.9.

### 5.3.1 활자 계급 — 4단 (2026-08-31 2차 회신 반영)

회신: *"숫자만 엄청 크고 다른 건 모두 하나의 느낌. 글·부가 정보가 작아 눈에 안 들어온다."*

| **T2 주장** | 맑은 고딕 700 | 21~25px | 회백 `#EAE7E0` | 그 영역이 말하는 한 줄 |

### A안 — Deep Navy · 정공법 (추천)
```
기본  #16202E  deep navy      +  #F7F5F2  warm off-white
강조  #EA002C  SK Red (핵심 숫자·개선 후)
보조  #7A8896  slate (종전·비교군)
```
표지·섹션 간지는 navy 전면, 본문은 off-white. **무게감이 가장 크고 본사 보고에 가장 안전.**
차트는 종전=slate / 개선=red 로 통일해 색만 봐도 before/after 가 읽힌다.

### B안 — Charcoal + Amber · 데이터 리포트
```
기본  #1F2328  charcoal       +  #FFFFFF  white
강조  #EA002C  red  ·  #C8912A  amber
```
차트가 주인공. 얇은 그리드에 숫자가 크다. **밀도가 가장 높다.**
다만 red + amber 조합이 자칫 산만해질 수 있어 강조 사용 규칙을 엄격히 잡아야 함.

### C안 — Off-white + Ink · 여백 중심
```
기본  #FAF8F5  off-white      +  #22262B  ink
강조  #EA002C  red  ·  #2E6E7E  teal
```
가장 세련되지만 여백이 커져 정보 밀도가 낮아진다. "밀도 있는 시각 요소" 요구와 상충 가능.

**제안**: A안을 기본으로, 차트 슬라이드만 B안의 밀도를 흡수하는 방향. 샘플 3장으로 확인.

### ② 디자인 샘플 — HTML 로 검토, PowerPoint 로 제작

이 환경에서는 `.pptx` 를 이미지로 렌더할 수 없다(⑤ 참조). 그래서 디자인 검토는
**HTML 목업**으로 하고, 확정된 좌표를 pptxgenjs 로 이식한다.

- 목업: `docs/ppt/design_samples.html` (1280×720 고정 좌표 = 13.333×7.5in @96dpi)
- 12컬럼 가이드 토글을 넣어 정렬을 눈으로 확인할 수 있다
- 폰트는 목업이 Gothic A1 / Noto Sans KR(웹폰트), 실제 PPT 는 **맑은 고딕**(윈도우 기본)
  → 자막폭이 달라 목업보다 PPT 가 약간 넓어질 수 있다. ⑤ 검증에서 보수적으로 잡는다.

### ⑤ 겹침 검증 — 이 환경의 제약과 대응

**제약을 먼저 밝힌다.** 이 환경에서는 `.pptx` 를 이미지로 렌더할 수 없다
(LibreOffice 변환 실패 확인, 한글 폰트는 Unifont·WenQuanYi 뿐 — 실제 맑은 고딕 자막폭과 다름).
따라서 **"눈으로 보고 확인"이 불가능**하다. 대신 기하 검증으로 대체한다:

| 검사 | 방법 | 통과 기준 |
|---|---|---|
| 경계 이탈 | 모든 shape 의 x+w, y+h vs 슬라이드 | 0건 |
| 상호 겹침 | 텍스트 박스 bbox 쌍별 교차 면적 | 0건 (의도적 배경 카드 제외) |
| 글자 넘침 | 한글 글자폭을 fontSize×0.98 로 **보수 추정** → 줄바꿈 후 필요 높이 vs 박스 높이 | 필요높이 ≤ 박스높이 × 0.9 |
| 여백 | 모든 요소가 외곽여백 0.6in 안쪽 | 0건 위반 |
| 대비 | 배경/글자 색 명도차 | WCAG AA 4.5:1 이상 |

한글 폭을 보수적으로(넉넉하게) 추정하므로 **검증을 통과하면 실제로는 여유가 남는다.**
그래도 최종 확인은 부장님 PC 에서 한 번 열어 보시는 것이 필요하다 — 이 점은 숨기지 않는다.
