### 목차 7개 — 지정 원문 (2026-08-31 수령)

```
1. 개요 및 추진 배경
2. 현황 파악 및 문제 정의
3. 데이터 분석 및 원인 규명(가설 검증)
4. 해결 방안 도출 및 예측/보정 모델 개발
5. 향후 추이 분석(모니터링 체계 구축)
6. 개선 효과(정량적/정성적)
7. 향후 계획 및 수평 전개 방안
```

이 7개가 **목차 장과 본문 15장 머리글의 원본**이다. `docs/ppt/build/theme.js` 의
`INDEX` 상수 한 곳에만 두었으므로, 표현을 고치면 목차 장과 머리글이 함께 바뀐다.
머리글은 `04   해결 방안 도출 및 예측/보정 모델 개발   ·   모델 선정` 처럼
목차 명칭 + 그 장의 세부 라벨로 나온다.

> 6번 원문은 `개선 효과(정량적/정석적)` 로 받았는데 **정성적**의 오타로 보아 그렇게 넣었다.
> 아니면 알려 주시면 상수 한 줄만 고친다.

**직책자 발표의 전제 3가지**
1. **결론이 앞에 있어야 한다.** 2번 슬라이드에서 이미 답이 보여야 한다.
2. **한 장에 메시지 하나.** 나열하면 흐름을 잃는다.
3. **숫자는 비교로 보여야 한다.** 절대값 하나는 의미가 없고 before/after가 의미다.

## 1. 핵심 메시지 — 이 발표가 남길 한 문장

> ### 사람의 판단 하나였던 보정값을, **데이터가 스스로 갱신하는 모델**로 바꿨습니다.

부제로 쓸 수치 세 개 (표지·요약·마무리에 반복 노출):

```
예측오차   3.83 → 1.29 MW   (66% ↓)
미달 회차  14건 → 3건        (79% ↓)
과대입찰   65.4 → 7.6 MW     (88% ↓)
```

*(누적 36건 LOOCV 기준. 종전 = 일괄 보정, 개선 = GP·RBF)*

## 2. 스토리라인 — 7개 목차를 하나의 흐름으로

```
매주 신고하는 숫자가 있다
      ↓  그 숫자를 온도와 무관한 '하나의 보정값'으로 맞춰 왔다
실제 편차는 -4.9 ~ +12.9 MW 로 온도에 따라 갈린다
      ↓  하나로 맞추면 겨울엔 과소(기회손실), 여름엔 과대(페널티)
왜 갈리는가 — 가설 4개를 세우고 3개를 데이터로 기각했다
      ↓  그럴듯한 설명을 계속 무너뜨린 끝에 남은 것: 온도 의존 잔차
물리 이론은 동결하고, 잔차만 온도별로 학습한다 (2단 구조)
      ↓  데이터가 36건뿐이라는 제약 — 커널 5종 · LOOCV · 층화 분리로 넘었다
커널 7종을 같은 자리에서 채점 → GP·RBF 가 전 지표 1위
      ↓  시운전에서 함정 3개를 만나고 전부 코드 가드로 못박았다
회차가 쌓이면 LOOCV 재학습으로 최적 모델을 다시 고른다 (자기 갱신)
      ↓
효과: 정량 3지표 + 정성 4관점 → 같은 구조 입찰 사업소로 수평 전개
```

**서사의 축은 "정확도 개선"이 아니라 "판단의 근거화"다.**
직책자가 사는 것은 MW 개선치가 아니라 *왜 그 숫자인지 설명할 수 있게 됐다*는 것이다.

## 3. 언어 원칙 — 전문용어를 쓰지 않는다

**대상은 본사 직책자다. 데이터 전문가가 아닌 분이 대부분이다.**
슬라이드에서 설명이 필요한 단어가 나오면 그 순간 청중은 내용을 놓친다.

### 규칙 3개

1. **슬라이드 본문은 쉬운 말로.** 전문용어는 괄호에 작게 병기한다.
   → `평균 오차 1.29 MW (MAE)` 처럼. 엔지니어도 헷갈리지 않고, 비전문가도 안 막힌다.
2. **제목은 라벨이 아니라 문장으로.**
   → ~~"가설 검증"~~ → **"그럴듯한 설명 4개를 의심했고, 3개는 틀렸습니다"**
3. **숫자에는 항상 방향을 붙인다.**
   → ~~"R² 0.85"~~ → **"설명력 0.85 — 1에 가까울수록 좋음"**

### 용어 치환표 (슬라이드에 쓸 표현)

| 원래 용어 | 슬라이드 표현 | 필요하면 이렇게 한 줄 설명 |
|---|---|---|
| LOOCV | **한 건씩 가리고 맞혀보기** | 정답 하나를 가리고 나머지로 맞혀본다. 36번 반복 — 모의고사와 같다 |
| MAE | **평균 오차** | 평균적으로 몇 MW 틀렸나 |
| RMSE | **큰 오차 가중 지표** | 크게 틀린 경우에 벌점을 더 준 오차 |
| R² | **설명력** | 0~1. 1에 가까울수록 잘 설명한다 |
| GP (가우시안 프로세스) | **부드럽게 잇는 방식** | 데이터가 있는 곳은 따르고, 없는 곳은 완만하게 잇는다 |
| 커널 (RBF·Matérn 등) | **잇는 방식** | 점과 점 사이를 어떤 모양으로 이을지 정하는 규칙 |
| 하이퍼파라미터 | (슬라이드에 쓰지 않음) | 사람이 정하지 않고 데이터가 정한다고만 말한다 |
| 잔차 | **이론과 실제의 차이** | |
| 층화 추출 | **온도대별로 골고루 나눠 뽑기** | 한쪽 온도대가 통째로 빠지지 않게 |
| 편차(bias·ME) | **치우침** | 계속 낮게 신고하는지 높게 신고하는지 |
| 허용밴드 | **허용 오차 범위 (±0.5%)** | |
| 스킬 점수 | **종전 방식 대비 개선율** | |
| 상관계수 r | **관련성** | +1 / −1 에 가까울수록 강한 관계 |
| 센서 드리프트 | **센서 값이 서서히 어긋나는 현상** | |
| OPC UA | **표준 통신 방식** | RiMS 서버와 직접 주고받는 산업 표준 |
| 2단 구조 | **이론 층 + 실적 보정 층** | |
| 내포 W | **숨어 있던 IGV 효과** | |
| 미달 / 과대입찰 / 기회손실 | (그대로 — 실무 용어) | |
| 보정값 | (그대로 — 담당자가 쓰는 말) | |

**시험 방법**: 각 슬라이드를 발전 업무를 모르는 사람에게 읽혔을 때
"무슨 말인지는 알겠다"가 나와야 한다. 안 나오면 그 문장은 고친다.

### 5.1 (폐기 · 이력용) 참고 샘플에서 가져왔던 12가지

> 왜 무엇을 바꿨는지는 §5.0. 아래는 판단 이력으로만 남긴다.

### 5.2 확정 팔레트 (v2)

```
기본  #0F1A28  딥 네이비 — 검정이 아니라 '푸른' 네이비   (배경)
      #0A1320  홈(groove) — 묶음 배경이 필요할 때만
      #EAE7E0  따뜻한 회백                            (본문 글자)
강조  #EFB13C  놋쇠 앰버   ← 개선·핵심 수치 (SK 오렌지 계열)
      #FF4D63  레드        ← 위험·미달 (어두운 바탕 가독성 보정)
                             인쇄용 채움에는 SK 레드 #EA002C
보조  #718BA6  슬레이트  (종전 방식 — 채워진 면: 막대·박스)
      #A8BCD1  밝은 슬레이트 (종전 방식 — 선: 그래프의 점선·침)
      #A9A79F  보조 설명 / #8A8880 라벨
      #2C425A  헤어라인 / #1F3244 더 약한 헤어라인
      #8A6620  앰버 어둡게 (열세 후보 막대)
```

**색의 의미를 고정한다 — 이게 이 발표의 핵심 장치다.**

| 색 | 뜻 | 쓰이는 곳 |
|---|---|---|
| 슬레이트 회색 | **종전 방식** | 일괄 보정 막대, 종전 눈금 |
| 놋쇠 앰버 | **개선 결과** | GP 막대·곡선, KPI 숫자, 결론 강조어 |
| 레드 | **위험·미달** | 미달 회차, 기각된 가설, 함정, 손실 구간 |

색만 보고도 "회색은 옛것, 앰버는 새것, 빨강은 위험"이 읽히게 한다.
슬라이드마다 색 뜻이 달라지면 청중은 매번 범례를 다시 읽어야 한다.

**선은 면보다 한 톤 밝게** — 2px 선은 같은 색의 채워진 면보다 훨씬 어둡게 보인다.
종전 방식을 막대·박스로 그릴 때는 `#5E7793`, **그래프의 점선·게이지 침으로 그릴 때는
`#8CA3BC`** 를 쓴다 (홈 면 위 대비 4.2:1 → 7.2:1). 굵기도 개선 곡선과 같은 2.6px 로 맞춘다 —
before/after 는 대등한 한 쌍이므로 한쪽만 얇으면 비교가 성립하지 않는다.

### 회색이 안 보이던 이유 — 명도가 아니라 색상 (2026-08-31 3차 회신)

회신: *"빨간색·노란색·흰색 글자는 잘 구분되는데 회색 글자가 은근히 잘 안 보인다."*

원인은 명도가 아니라 **색상**이었다. 남색 바탕(`#0F1A28`)에 **푸른 회색** 글자를 얹으면
명도차가 있어도 색상이 같은 계열이라 바탕에 묻힌다. 빨강·노랑·흰색이 잘 보였던 것은
색상이 반대편이라 명도 말고 색상으로도 갈렸기 때문이다.

→ **중립색 계열을 전부 '따뜻한 회색'으로 돌렸다.** 종전 방식(슬레이트)만 푸른 계열로
남긴다 — 앰버(개선)와 반대편이어야 뜻이 갈리기 때문이다.

| 용도 | 이전 | 현재 | 대비 (배경 기준) |
|---|---|---|---|
| 본문 문장 | `#BCC9D6` | **`#CFCBC2`** | 10.4 → **10.8 : 1** |
| 캡션·부가 | `#93A6BA` | **`#A9A79F`** | 7.0 → **7.3 : 1** |
| 라벨 | `#63798F` | **`#8A8880`** | 3.9 → **4.9 : 1** |
| 종전 — 면 | `#5E7793` | **`#718BA6`** | 3.8 → **5.0 : 1** |
| 종전 — 선 | `#8CA3BC` | **`#A8BCD1`** | 6.7 → **9.0 : 1** |

**진단의 근거** — 본문은 바꾸기 전에도 이미 **10.4:1** 이었다. 그런데도 안 보였다는 것이
명도 문제가 아니라는 증거다. 색상을 바꾼 것이 효과의 대부분이고, 명도는 부수적으로
올렸다. 다만 라벨(3.9:1)과 종전 면(3.8:1)은 WCAG AA(4.5:1) 미달이기도 했다.
이제 전 색이 AA 를 넘는다: 회백 14.2 · 본문 10.8 · 앰버 9.2 · 종전선 9.0 · 캡션 7.3 ·
레드 5.4 · 종전면 5.0 · 라벨 4.9.

### 5.3 레이아웃 규격 (v2)

목업이 1280×720 고정좌표이므로 **px ÷ 96 = in** 으로 그대로 pptxgenjs 에 넣는다.

```
그리드    12컬럼 · 거터 0.18in(17.28px) · 컬럼폭 78.16px
──────────────────────────────────────────────────────────
 44px  0.46in ─ 섹션명 (12px≈9pt, mono, 자간 .16em) │ 우상단 7눈금 계기

```

### 5.3.1 활자 계급 — 4단 (2026-08-31 2차 회신 반영)

회신: *"숫자만 엄청 크고 다른 건 모두 하나의 느낌. 글·부가 정보가 작아 눈에 안 들어온다."*

| **T1 데이터** | Consolas 700 | 30~50px (표지 48 · KPI 44 · 인용 25) | 앰버 `#EFB13C` | 숫자만 |

**폰트 규칙** — 한글 **맑은 고딕**, 숫자·영문 라벨 **Consolas**.
굵기는 **400·700 만** 쓴다 (맑은 고딕에 800 이 없어 v1 은 PPT 에서 다르게 나올 수 있었다).

### A안 — Deep Navy · 정공법 (추천)
```
기본  #16202E  deep navy      +  #F7F5F2  warm off-white
강조  #EA002C  SK Red (핵심 숫자·개선 후)
보조  #7A8896  slate (종전·비교군)
```
표지·섹션 간지는 navy 전면, 본문은 off-white. **무게감이 가장 크고 본사 보고에 가장 안전.**
차트는 종전=slate / 개선=red 로 통일해 색만 봐도 before/after 가 읽힌다.

### B안 — Charcoal + Amber · 데이터 리포트
```
기본  #1F2328  charcoal       +  #FFFFFF  white
강조  #EA002C  red  ·  #C8912A  amber
```
차트가 주인공. 얇은 그리드에 숫자가 크다. **밀도가 가장 높다.**
다만 red + amber 조합이 자칫 산만해질 수 있어 강조 사용 규칙을 엄격히 잡아야 함.

### C안 — Off-white + Ink · 여백 중심
```
기본  #FAF8F5  off-white      +  #22262B  ink
강조  #EA002C  red  ·  #2E6E7E  teal
```
가장 세련되지만 여백이 커져 정보 밀도가 낮아진다. "밀도 있는 시각 요소" 요구와 상충 가능.

**제안**: A안을 기본으로, 차트 슬라이드만 B안의 밀도를 흡수하는 방향. 샘플 3장으로 확인.

### 가설 검증 4건 (7번 슬라이드)

| 가설 | 판정 | 근거 |
|---|---|---|
| 2025 상반기는 설비 수준이 다른 시기다 (−4.09 MW) | **기각** | 내포 W 5건 평균 +0.09 → IGV 미실시가 원인 |
| 진공 잔차로 보정값을 예측할 수 있다 | **기각** | n=5 r=−0.85 → n=36 r=+0.09. 표본 5개의 과대해석 |
| 담당자 표와의 이론값 차이는 진공 항 때문이다 | **기각** | 58건 대조 → Δ = −2.196 + 0.1183×CIT (곡선 차이) |
| 진공도는 외기온도의 함수다 | **채택** | 진공도 = 33.64 + 1.242 × CIT, r = **+0.947** |

### 시운전 함정 3건 (12번 슬라이드)

### ② 디자인 샘플 — HTML 로 검토, PowerPoint 로 제작

이 환경에서는 `.pptx` 를 이미지로 렌더할 수 없다(⑤ 참조). 그래서 디자인 검토는
**HTML 목업**으로 하고, 확정된 좌표를 pptxgenjs 로 이식한다.

- 목업: `docs/ppt/design_samples.html` (1280×720 고정 좌표 = 13.333×7.5in @96dpi)
- 12컬럼 가이드 토글을 넣어 정렬을 눈으로 확인할 수 있다
- 폰트는 목업이 Gothic A1 / Noto Sans KR(웹폰트), 실제 PPT 는 **맑은 고딕**(윈도우 기본)
  → 자막폭이 달라 목업보다 PPT 가 약간 넓어질 수 있다. ⑤ 검증에서 보수적으로 잡는다.

### ⑤ 겹침 검증 — 이 환경의 제약과 대응

**제약을 먼저 밝힌다.** 이 환경에서는 `.pptx` 를 이미지로 렌더할 수 없다
(LibreOffice 변환 실패 확인, 한글 폰트는 Unifont·WenQuanYi 뿐 — 실제 맑은 고딕 자막폭과 다름).
따라서 **"눈으로 보고 확인"이 불가능**하다. 대신 기하 검증으로 대체한다:

| 검사 | 방법 | 통과 기준 |
|---|---|---|
| 경계 이탈 | 모든 shape 의 x+w, y+h vs 슬라이드 | 0건 |
| 상호 겹침 | 텍스트 박스 bbox 쌍별 교차 면적 | 0건 (의도적 배경 카드 제외) |
| 글자 넘침 | 한글 글자폭을 fontSize×0.98 로 **보수 추정** → 줄바꿈 후 필요 높이 vs 박스 높이 | 필요높이 ≤ 박스높이 × 0.9 |
| 여백 | 모든 요소가 외곽여백 0.6in 안쪽 | 0건 위반 |
| 대비 | 배경/글자 색 명도차 | WCAG AA 4.5:1 이상 |

한글 폭을 보수적으로(넉넉하게) 추정하므로 **검증을 통과하면 실제로는 여유가 남는다.**
그래도 최종 확인은 부장님 PC 에서 한 번 열어 보시는 것이 필요하다 — 이 점은 숨기지 않는다.
