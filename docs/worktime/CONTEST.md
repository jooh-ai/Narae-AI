## 3. AI 활용 업무개선 사례

### 3-1. 개선 전 문제점  *(가이드 3~5줄)*

```
1. 위례사업소는 선택적 근로시간제를 시행하면서, 매일 8시간 이상 근무자를 전체 인원의
   30%(23명 기준 7명) 이상 유지하고 그중 직책자가 1명 이상 포함되어야 한다.
2. 이를 Teams에 올린 그룹별 엑셀 3개에 각자 수기로 적고, 30% 충족 여부는 날짜마다
   사람 수를 직접 세어 확인했다 — 월 20일 × 3개 그룹 = 월 60회 반복 집계.
3. 코어타임(08:30~11:30)·반차를 붙일 수 있는 시각·휴게 공제 같은 규칙이 표에
   없어, 불가능한 조합(예: 오전반차 09:00~14:00)도 그대로 입력되고 뒤늦게 발견됐다.
4. 30% 미달일이 생겨도 "누구와 근무를 바꿔야 하는지"는 표를 눈으로 훑어야 알 수 있었다.
5. 개인별 월 총량·OT 누적/잔여·탄력근무 주 52/64시간은 별도 수기 계산이라 확인이 늦고
   계산 오류가 났다.
```

### 3-2. AI 활용 방법  *(가이드 3~5줄 · 도구명 기재 권장)*

```
1. Claude(Claude Code)와 대화하며 취업규칙과 실제 운영 사례를 정리해, 판정 규칙 7가지
   (코어타임 완전 피복 · 반차 블록 역산 · 휴게시간 경계 등)를 도출했다.
   가능/불가능 사례를 목록으로 외우는 대신 규칙으로 일반화한 것이 핵심이다.
2. 그 규칙을 Node.js 코드로 30분 격자 전체에 돌려, 규정을 통과하는 근무 조합
   106가지를 자동 추출하고, 전달받은 운영 사례 90개 단정으로 자가검증했다.
3. SharePoint 목록 5개 설계, 가져오기용 CSV, Power Apps 화면과 Power Fx 수식
   (연쇄 드롭다운 · 30% 판정 · 조율 후보 · OT · 탄력근무)을 AI와 함께 작성했다.
4. SharePoint도 Power Apps도 이번에 처음 써 봤다. 목록 만들기부터 수식 오류
   (위임 경고 · 날짜 시간대 불일치 · 갤러리 중첩)까지, 막히면 화면을 캡처해 물어보고
   원인과 수정 수식을 받아 해결했다 — 개발 경험 없이 완성했다.
5. 규칙이 바뀌면 코드를 다시 돌려 106행짜리 조합표만 교체하도록, 규칙을 코드가 아닌
   데이터(SharePoint 목록)로 분리했다.
```

### 3-3. 개선 내용 / 실행 과정  *(가이드 5~8줄)*

```
1. 규칙 도출 → 유효 조합 106가지 자동 생성 → 자가검증(90개 단정 전부 일치) 순으로
   판정 엔진을 먼저 확정하고, 화면은 그다음에 만들었다.
2. 데이터는 SharePoint 목록 5개(조합표 106행 · 명부 · 공휴일 · 월설정 · 근태기록)에
   두고 CSV로 일괄 등록했다. 앱이 아니라 이 목록이 계산의 원천이다.
3. 앱은 Teams 안의 Power Apps로 만들어 탭 하나로 열리게 했다. 화면은 5개 —
   매트릭스 / 월 달력·30% / 근태 입력 / 개인 요약·OT / 탄력근무 52·64.
4. 입력은 연쇄 드롭다운으로 바꿨다. 유형을 고르면 출근 시각이, 출근을 고르면 퇴근
   시각이 걸러진다. 규정에 없는 조합은 목록에 아예 뜨지 않아 원천 차단된다.
5. 빈칸 = 8시간 정상근무로 정의해, 8시간을 채우지 못하는 날만 입력한다. 기존 수기
   방식의 습관을 그대로 살려 입력 부담을 늘리지 않았다.
6. 저장하는 순간 날짜별 8시간 인원 · 30% 충족 · 직책자 포함 여부가 다시 계산된다.
   미달일은 빨갛게 뜨고, 바꿀 수 있는 사유(반차 · 8시간 미만)인 사람만 조율 후보로
   올라온다 — 출장 · 교육 · 연차는 애초에 제외된다.
7. 개인 화면에서 조정 총량(휴가 차감) · 실근로 누적 · OT 한도/잔여 · 주별 64시간을,
   대정비 달은 3개월 평균 주 52시간까지 한 화면에서 확인한다.
8. 현재 테스트 채널에서 시험 운영 중이며, 검증이 끝나면 두 팀이 함께 쓰는 채널의
   탭으로 옮긴다.
```

### 3-4. 달라진 점 / 개선 효과 (정량 · 정성)  *(가이드 3~5줄 · 수치 기재)*

```
1. [정량] 날짜별 30% 충족 집계가 월 60회 수작업 → 0회. 저장 즉시 자동 판정되고,
   취합 담당자 없이 23명이 각자 동시에 입력·저장한다(엑셀 파일 3개 → 목록 1개).
2. [정량] 오입력이 구조적으로 사라졌다. 유형 11 × 출근 6 × 퇴근 18 = 1,188가지 중
   규정을 통과하는 106가지만 드롭다운에 노출되어, 불가능한 조합은 고를 수가 없다.
3. [정량] 개인 월 총량 · OT 누적/잔여 수기 계산 연 276건(23명 × 12개월) → 0건.
   휴가에 따른 총량 차감과 OT 한도 가산도 자동으로 따라온다.
4. [정량] 월 취합·대사에 쓰던 시간 약 3~4시간 → 10분 내외(테스트 운영 기준 자체 추정).
5. [정성] 미달일과 조율 후보가 바로 보여 "누구와 바꿀지" 찾는 작업이 없어졌고,
   판정 근거가 기록으로 남아 팀장 승인·소명 자료로 그대로 쓴다.
```

### 3-5. 확산 가능성  *(가이드 2~4줄)*

```
1. 광양 · 파주 · 하남 · 여주 · 이천 · 청주 사업소도 동일한 규정과 절차를 따르므로,
   규칙표(106행)와 공휴일은 그대로 쓰고 명부와 월설정(정규 근로시간 · OT 기본시간)만
   바꾸면 적용된다. 사업소당 반나절이면 올릴 수 있다.
2. 목록에 「사업소」 열 하나만 추가하면 앱 하나로 전 사업소를 운영할 수 있고,
   규정이 개정될 때 조합표를 한 번만 고치면 전 사업소에 동시에 반영된다.
3. 근태뿐 아니라 규칙이 명확한 반복 판정 업무(작업허가 검토 · 교대 배치 · 정비 인원
   편성)에 「규칙 도출 → 유효 조합표 → 앱에서 조회」라는 같은 구조를 그대로 쓸 수 있다.
4. 고도화 방향 — 계획/실적 2계층 관리, 파트장·팀장 승인 상태 기록,
   8시간 부담 형평성 집계, Power BI 연계.
```

### 3-6. 기타 느낀 점

```
1. 가장 크게 배운 건 "사례를 모으는 것과 규칙을 세우는 것은 다르다"는 점이다.
   AI에 사례를 주고 규칙으로 일반화한 뒤 30분 격자 전체를 돌려 보니, 사람이 놓치고
   있던 예외 3가지가 그때 드러났다. 목록으로만 관리했다면 계속 몰랐을 것이다.
2. SharePoint도 Power Apps도 처음이었는데, 막힐 때마다 오류 화면을 캡처해 물어보면
   원인과 고칠 수식을 함께 받을 수 있었다. 개발자가 아니어도 만들 수 있다는 걸
   직접 확인한 것이 가장 큰 수확이다.
3. AI가 코드를 대신 써 주는 것보다, 무엇을 만들지 정리해 주는 역할이 더 컸다.
   말로 풀어 놓은 요구사항을 구조로 바꿔 주고 빠진 조건을 되물어 준다.
4. 다만 판정 기준이 맞는지는 사람이 확인해야 한다. 자가검증 케이스 90개를 먼저
   만들어 둔 것이 규칙을 고칠 때마다 안전장치가 됐다.
```

## 5. 다른 사업소 확산 — 실제로 얼마나 손이 가나

| 목록 | 광양 · 파주 · 하남 · 여주 · 이천 · 청주에서 | 작업량 |
|---|---|---|
| `조합표` (106행) | **그대로** — 규정이 같으면 유효 조합도 같다 | 0 |
| `공휴일` | **그대로** — 창립기념일만 확인 | 0 |
| `명부` | 그 사업소 인원으로 교체 (CSV 한 번) | 10분 |
| `월설정` | 정규 근로시간 · OT 기본 가능시간만 사업소 값 | 10분 |
| `근태기록` | 빈 목록으로 시작 | 0 |
| 앱 | 복제 후 데이터 원본 5개를 그 사이트로 다시 연결 | 30분 |

**Power Fx 수식은 한 줄도 고치지 않는다.** 판정 기준이 전부 목록에서 읽히도록
만들어 둔 결과다(모수·필요 인원은 명부에서, 소정근로일은 공휴일에서,
정규 종료·OT 기본은 월설정에서).

### 더 나은 방향 — 앱 하나로 전 사업소

`명부` · `월설정` · `근태기록` 에 **`사업소` 열 하나**를 추가하고,
`App.OnStart` 의 읽기 구문 세 곳에 필터를 더하면 된다.

```powerfx
Set(gvSite, LookUp(명부, Lower(사용자.Email) = Lower(User().Email)).사업소);
ClearCollect(colAll, Filter(명부, 사업소 = gvSite));
ClearCollect(colRec, Filter(근태기록, 사업소 = gvSite, 근무일 >= gvMonthStart, 근무일 <= gvMonthEnd))
```

- 로그인한 사람의 사업소를 명부에서 읽어 그 사업소만 보여 준다
- 규정이 바뀌면 **조합표를 한 번만 교체**해도 전 사업소에 반영된다
- 사업소를 늘릴 때 할 일은 **명부에 행을 추가하는 것뿐**

처음 한두 사업소는 복제로 빠르게 올리고, 세 곳을 넘어가면 통합형으로 합치는 것이
유지보수 관점에서 유리하다.
