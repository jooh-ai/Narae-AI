## 2. 사례 개요

### 사례명

```
매일 8시간 근무 인원 30% 맞추기를 자동화한 근태 앱 (AI 설계 + Power Apps)
```

```
AI로 만든 근태 관리 앱 — 30% 필수인원과 초과근무를 저장 즉시 자동 계산
```
```
휴가 쓸 때마다 엑셀을 세던 일을 없앤 근태 앱 (AI 규칙 정리 + SharePoint · Power Apps)
```

## 3. AI 활용 업무개선 사례

### 3-1. 개선 전 문제점  *(가이드 3~5줄)*

```
1. 위례사업소는 선택적 근로시간제를 쓰고 있어서, 매일 8시간을 채워 일하는 사람이
   전체의 30%(23명 기준 7명) 이상이어야 하고 그 안에 직책자가 1명은 들어가야 한다.
2. 이걸 Teams에 올린 그룹별 엑셀 3개에 각자 손으로 적는데, 휴가를 쓰거나 일찍 퇴근하려면
   그 엑셀 3개를 열어 그 날 8시간 인원이 되는지 본인이 직접 세어 봐야 했다.
3. 코어타임(08:30~11:30)이나 반차를 붙일 수 있는 시각, 휴게시간 공제 같은 규칙은
   엑셀에 나타나지 않아, 규정에 안 맞는 근무(예: 오전반차 09:00~14:00)도 그대로 들어갔다.
4. 각자 따로 보고 판단하다 보니 두 사람이 같은 날을 잡아 30%가 깨져도 나중에야 알았고,
   누구와 근무를 바꿔야 할지는 표를 눈으로 훑어 찾아야 했다.
5. 개인별 월 근무시간, OT 쓴 시간과 남은 시간, 탄력근무 주 52/64시간은 따로 계산해야
   해서 확인이 늦고 틀리는 일이 있었다.
```

### 3-2. AI 활용 방법  *(가이드 3~5줄 · 도구명 기재 권장)*

```
1. Claude(Claude Code)와 대화하면서 취업규칙과 실제 사례를 정리해, 근무를 인정할지
   판단하는 규칙 7가지를 뽑아냈다. 사례를 목록으로 외우지 않고 규칙으로 만든 것이 핵심이다.
2. 그 규칙을 코드(Node.js)로 만들어 30분 단위로 나올 수 있는 근무 조합을 전부 검사했다.
   규정에 맞는 106가지가 자동으로 걸러졌고, 실제 사례 90가지로 맞는지 확인했다.
3. SharePoint 목록 5개 설계, 목록에 넣을 CSV 파일, Power Apps 화면과 수식(Power Fx)까지
   AI와 같이 만들었다.
4. SharePoint도 Power Apps도 이번이 처음이었다. 목록 만드는 것부터 수식 오류까지,
   막히면 화면을 캡처해 물어보고 원인과 고칠 수식을 받아 해결했다.
5. 규정이 바뀌면 코드를 다시 돌려 106줄짜리 표만 바꾸면 되도록, 규칙을 앱이 아니라
   데이터(SharePoint 목록)에 넣어 두었다.
```

### 3-3. 개선 내용 / 실행 과정  *(가이드 5~8줄)*

```
1. 규칙 뽑기 → 가능한 조합 106가지 자동 생성 → 사례 90가지로 확인. 판단 기준을 먼저
   확정하고 화면은 그다음에 만들었다.
2. 데이터는 SharePoint 목록 5개(조합표 106줄 · 명부 · 공휴일 · 월설정 · 근태기록)에 두고
   CSV로 한 번에 올렸다. 앱이 아니라 이 목록이 계산의 기준이다.
3. 앱은 Teams 안의 Power Apps로 만들어 탭 하나로 열리게 했다. 화면은 5개 —
   매트릭스 / 월 달력·30% / 근태 입력 / 개인 요약·OT / 탄력근무 52·64.
4. 입력 칸을 서로 연결했다. 유형을 고르면 그에 맞는 출근 시각만, 출근을 고르면 맞는
   퇴근 시각만 남는다. 규정에 없는 조합은 목록에 아예 안 보여서 고를 수가 없다.
5. 빈칸을 8시간 정상근무로 정했다. 8시간을 못 채우는 날만 적으면 되니, 지금까지 해 오던
   방식 그대로여서 입력 부담이 늘지 않는다.
6. 저장하면 그 즉시 날짜별 8시간 인원과 30% 충족 여부, 직책자 포함 여부가 다시 계산된다.
   모자란 날은 빨갛게 뜨고, 근무를 바꿀 수 있는 사람(반차·8시간 미만)만 후보로 올라온다.
7. 개인 화면에서는 그 달에 채워야 할 시간과 실제 근무시간, OT 남은 시간, 주별 64시간을,
   대정비 달에는 3개월 평균 주 52시간까지 한 화면에서 본다.
8. 지금은 테스트 채널에서 시험 운영 중이고, 확인이 끝나면 두 팀이 함께 쓰는 채널로 옮긴다.
```

### 3-4. 달라진 점 / 개선 효과 (정량 · 정성)  *(가이드 3~5줄 · 수치 기재)*

```
1. [정량] 휴가나 근무시간 조정을 하려면 엑셀 3개를 열어 그 날 8시간 인원을 직접 세어
   봐야 했다. 23명이 각자 하던 이 확인이 0이 됐다 — 앱을 열면 날짜마다 숫자가 이미
   떠 있다(엑셀 3개 → 목록 1개, 23명이 같은 화면을 본다).
2. [정량] 잘못 입력할 방법이 없어졌다. 유형 11 × 출근 6 × 퇴근 18 = 1,188가지 중
   규정에 맞는 106가지만 목록에 뜨기 때문이다.
3. [정량] 개인 월 근무시간과 OT 남은 시간 손계산 연 276건(23명 × 12개월) → 0건.
   휴가를 쓰면 채워야 할 시간과 OT 한도가 자동으로 따라 바뀐다.
4. [정량] 확인하고 맞춰 보는 데 쓰던 시간 월 3~4시간 → 10분 안팎(시험 운영 기준, 자체 추정).
5. [정성] 전에는 각자 따로 보고 판단해 같은 날이 겹쳐도 나중에야 알았는데, 이제는 모두가
   같은 기록을 봐서 그 자리에서 드러난다. 판단 근거도 남아 팀장 승인 자료로 그대로 쓴다.
```

### 3-5. 확산 가능성  *(가이드 2~4줄)*

```
1. 광양 · 파주 · 하남 · 여주 · 이천 · 청주도 규정과 절차가 같으므로, 규칙표(106줄)와
   공휴일은 그대로 두고 명부와 월설정(정규 근무시간 · OT 기본시간)만 바꾸면 된다.
   수식은 한 줄도 고치지 않는다.
2. 목록에 「사업소」 칸 하나만 넣으면 앱 하나로 모든 사업소를 쓸 수 있고, 규정이 바뀌면
   표를 한 번만 고쳐도 전 사업소에 같이 반영된다.
3. 근태 말고도 규칙이 분명한 반복 판단 업무(작업허가 검토 · 교대 배치 · 정비 인원 편성)에
   「규칙 정리 → 가능한 조합표 → 앱에서 찾아보기」라는 같은 방식을 쓸 수 있다.
4. 앞으로 더할 것 — 계획과 실적 나눠 보기, 파트장 · 팀장 승인 기록,
   8시간 부담 형평성 집계, Power BI 연계.
```

### 3-6. 기타 느낀 점

```
1. 사례를 모으는 것과 규칙을 세우는 것은 다르다는 걸 배웠다. AI에 사례를 주고 규칙으로
   바꾼 뒤 모든 경우를 돌려 보니, 우리가 놓치고 있던 예외 3가지가 그때 나왔다.
2. SharePoint도 Power Apps도 처음이었는데, 막힐 때마다 오류 화면을 캡처해 물어보면
   원인과 고칠 방법을 같이 받을 수 있었다. 개발자가 아니어도 만들 수 있었다.
3. AI가 코드를 대신 써 주는 것보다, 무엇을 만들지 정리해 주는 역할이 더 컸다.
   말로 늘어놓은 요구사항을 구조로 바꿔 주고 빠진 조건을 되물어 준다.
4. 다만 판단 기준이 맞는지는 사람이 봐야 한다. 확인용 사례 90가지를 먼저 만들어 둔 것이
   규칙을 고칠 때마다 안전장치가 됐다.
```

## 5. 다른 사업소 확산 — 실제로 얼마나 손이 가나

| 목록 | 광양 · 파주 · 하남 · 여주 · 이천 · 청주에서 | 작업량 |
|---|---|---|
| `조합표` (106행) | **그대로** — 규정이 같으면 유효 조합도 같다 | 0 |
| `공휴일` | **그대로** — 창립기념일만 확인 | 0 |
| `명부` | 그 사업소 인원으로 교체 (CSV 한 번) | 10분 |
| `월설정` | 정규 근로시간 · OT 기본 가능시간만 사업소 값 | 10분 |
| `근태기록` | 빈 목록으로 시작 | 0 |
| 앱 | 복제 후 데이터 원본 5개를 그 사이트로 다시 연결 | 30분 |

**Power Fx 수식은 한 줄도 고치지 않는다.** 판정 기준이 전부 목록에서 읽히도록
만들어 둔 결과다(모수·필요 인원은 명부에서, 소정근로일은 공휴일에서,
정규 종료·OT 기본은 월설정에서).

### 더 나은 방향 — 앱 하나로 전 사업소

`명부` · `월설정` · `근태기록` 에 **`사업소` 열 하나**를 추가하고,
`App.OnStart` 의 읽기 구문 세 곳에 필터를 더하면 된다.

```powerfx
Set(gvSite, LookUp(명부, Lower(사용자.Email) = Lower(User().Email)).사업소);
ClearCollect(colAll, Filter(명부, 사업소 = gvSite));
ClearCollect(colRec, Filter(근태기록, 사업소 = gvSite, 근무일 >= gvMonthStart, 근무일 <= gvMonthEnd))
```

- 로그인한 사람의 사업소를 명부에서 읽어 그 사업소만 보여 준다
- 규정이 바뀌면 **조합표를 한 번만 교체**해도 전 사업소에 반영된다
- 사업소를 늘릴 때 할 일은 **명부에 행을 추가하는 것뿐**

처음 한두 사업소는 복제로 빠르게 올리고, 세 곳을 넘어가면 통합형으로 합치는 것이
유지보수 관점에서 유리하다.
